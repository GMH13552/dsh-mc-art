# AI 做模组的流程：我们现在的样子，和别人在做什么

这不是一篇综述，是一次**自查**。起因是两句反馈：

> 「我们现在的设计流程感觉可能有优化的空间，你可以广泛看看现在的 AI 的 mod 制作是怎么流程的」
> 「我总觉得我们生成的代码风格包括美术风格，都不算很好的能生成的感觉」

下面分三部分：我们现在的流程长什么样（含问题定位）、外面能找到的做法（标注哪些只是从摘要看到、
没有逐条验证）、以及按性价比排序的改法。

## 一、我们现在的流程，以及"感觉不好"从哪里来

现状：`mc-mod` skill 的 stage 0–7（定目标 → 定内容 → 美术 → atlas → 代码/资源 → 游戏内验证 →
人眼验证 → 分支），配一个面板（看/改资产）、一个美术引擎（`mc-art`，确定性栅格化）、一个裁判
（GameTestServer，退出码 = 失败数）。

**问题 1：代码是"一次写成"的，没有脚手架**
模型直接写 Java 和资源 JSON。每个方块/物品的注册代码都由模型重新组织一遍，于是：
- 同一个工程里出现多种写法（注册顺序、判空风格、字段命名不一致）；
- 样板代码（注册、`BlockBehaviour.Properties`、掉落表）每次重写，出错面大；
- 没有格式化门禁，缩进/换行随模型心情。

**问题 2：资源 JSON 手写，而不是生成**
`assets/<ns>/models/block/*.json`、`blockstates/*.json`、`lang`、drop 表，都是模型逐个写的。
一个族 12 个方块 = 几十个 JSON，任何一个字段写错都要靠"画不出来"才发现。Fabric 官方文档给的
标准做法是 **datagen**（用代码生成资源，见 [Fabric Tag Generation](https://docs.fabricmc.net/develop/data-generation/tags)）；
我们有一半是手写的。

**问题 3：美术没有"中间产物"**
现在是"参考 → 直接出图 → 眼睛看"。缺三样东西：
- **风格卡**（这个 mod 的调色板区间、明度范围、强调色预算、形状语法）——没有它，每个族都从零猜；
- **显式语料**（这次参考了哪几张原版图，为什么是它们）——参考靠模型记忆，出错时无法复查；
- **度量报告**（palette/直方图/孤立像素/接缝）——有引擎能力，但没有把结果变成"必须看的一份报告"。

**问题 4：每个阶段的"证据"不统一**
有的阶段留了命令与输出，有的只有一句"已完成"。所以出问题时只能回读对话，
而不是读一份可复现的证据文件。

## 二、外面在做什么（只写摘要里能看到的，未逐条验证）

- **把工具做成 MCP / 结构化工具，模型在循环里用编译器当裁判**：
  [`langyo/minecraft-mod-mcp`](https://github.com/langyo/minecraft-mod-mcp)、
  [`@ndellagrotte/cleanroom-modding-mcp`](https://www.npmjs.com/package/@ndellagrotte/cleanroom-modding-mcp)。
  共同点：构建/运行/读日志是**工具**，不是让模型写脚本；失败信息回到模型手里继续改。
- **GUI 生成器 + AI 外壳**：[`WayaSteurbautYT/mcreator-ai-plugin`](https://github.com/WayaSteurbautYT/mcreator-ai-plugin)、
  [`Nxkoo/MCreator-Agent`](https://github.com/nxkoo/mcreator-agent)。共同点：产物来自**模板 + 表单**，
  模型只填字段——所以风格天然统一。
- **资源用 datagen 生成**：Fabric 官方文档
  [Tag Generation](https://docs.fabricmc.net/develop/data-generation/tags) / Tinkers' Construct 的
  `src/generated/README`（[链接](https://github.com/slimeknights/tinkersconstruct/blob/f4e77d43f39ba1047bf93ae816b7e1beaab514c2/src/generated/README.md)）。
- **美术一致性被当成独立问题**：有人在做 style-consistency engine
  （[project-forge#6840](https://github.com/Tristan578/project-forge/issues/6840)）。

一句话：**别人把"生成"变成"填规格 + 模板产出 + 编译器/度量当裁判"；我们现在还有相当一部分是
"模型直接写产物 + 人眼看"**。这不是模型不行，是流程没把确定性放到该放的地方。

## 三、建议（按性价比排序）

### A. 规格先行（spec-first）：一份 `mod.spec.json` 是唯一真相
把方块/物品/族/风格卡/命名写成一份结构化规格（字段少而硬），代码与资源都从它生成。
模型改 spec（小、稳定、可校验），不直接改产物。收益：风格统一、可 diff、可回滚，
也让"再生成一次"变成有意义的操作。

### B. 脚手架 + 格式化门禁
固定 Java 模板（主类、注册类、事件接线、资源位置），模型只填 spec。加一个格式化门禁
（google-java-format 或 spotless，版本钉死），跑不过就不算完成。收益：代码风格问题从"靠自觉"
变成"过不了门禁"。

### C. 美术三件套：风格卡 + 语料 + 度量报告
- **风格卡**：每个 mod 一份（参考实现里 `dsh-media-desk` 的"风格卡"就是把写作风格变成一张卡，
  同样的思路可以搬到美术）；
- **语料**：这次参考哪几张原版图、为什么（角色/层级/明度）；
- **度量报告**：生成后自动出一份（调色板、明度直方图、孤立像素、接缝），不达标就只重生成那个族。
  已有引擎能力，缺的是"必须看它"的流程位置。

### D. 每阶段一份证据文件
`docs/evidence/stage-N.md`：跑了什么命令、输出是什么、截图/diff 在哪。面板里能直接打开。
收益：出问题时读证据，不读对话。

### E. 面板加一页"风格与流程"
把风格卡、语料、最近一次度量、门禁结果做成卡片（正好对上 v2 的卡片语言）。
这是"看和改"之外，面板第一次承担"解释这一步为什么算过"。

## 四、落地顺序

1. **B + D**（一周内能见效）：脚手架/格式化门禁、证据文件模板。代码风格的观感立刻统一。
2. **C**（最影响"美术好不好"）：把风格卡与度量报告接进 stage 3/4，先只对**一个族**做闭环，
   再推广。
3. **A**（结构性改动）：spec-first 会动到引擎与 skill 的接口，放最后一轮，避免中途返工。
4. **E** 跟着 A/C 的产物走，最后做。

## 五、还没验证的部分

- 上面三个外部项目的**具体工具清单与循环细节**没有逐条验证（GitHub 页面抓取被导航栏截断、
  raw README 拉取失败），只有搜索摘要层面的信息；引用它们是为了说明方向，不是当作结论。
- 我们现有流程里"手写 JSON 占多大比例"没有量化（需要一次真实工程统计）。
- `mc-art` 引擎的度量能不能直接产出"风格卡"需要的字段，还没有核对。
